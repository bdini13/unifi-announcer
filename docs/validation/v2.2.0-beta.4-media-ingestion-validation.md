## Single-Chime checks — 2026-10-30

The [live validation record](reliability-single-chime-2026-10-30.md) distinguishes
listener-confirmed playback from API results and automated coverage. Native
Home Assistant `tts.speak` through Piper reached `/media/announce` and played
clearly once. Direct WAV upload also normalized and played correctly. Text
ordering, repeated speech during a backend restart, and post-restart speech
passed with a listener. Rejected media left slot state unchanged.

On the October 31 physical reboot repeat, the first request after reconnect
received Protect HTTP 500 and Announcer HTTP 502/failed. A deliberate later
attempt after the uncertainty guard expired played clearly once. Immediate
post-reconnect readiness remains unresolved; delayed success does not close
that recovery gate. The original backend was restored after testing.

These results do not close the full checklist below. The installed HA client
was not updated to the candidate source; repeated native HA requests, camera
and mixed-device paths, saved Protect presets, and the final frozen revision
still need their own evidence. The synthetic `package-delivered` preset is
slot-backed speech and cannot substitute for a saved Protect audio test.

## Gate 1 — native `tts.speak` to one Smart Chime

1. Select a Home Assistant TTS provider that is known to synthesize correctly.
2. Target one UniFi Announcer Smart Chime media-player entity with `tts.speak`.
3. Use a unique phrase that cannot be confused with cached prior speech.
4. Observe the Home Assistant action result and Announcer logs/status.
5. Confirm in the room that the exact phrase is audible and intelligible once.

Pass criteria:

- [ ] HA resolves a media-source item and calls the Announcer media path.
- [ ] Announcer accepts/normalizes the audio and returns a canonical non-failure disposition.
- [ ] The intended Smart Chime plays the expected phrase once.
- [ ] No unintended target produces audio.
- [ ] Last playback result updates consistently with the dispatcher outcome.

## Gate 2 — repeated native `tts.speak` / fixed-slot behavior

Run the same phrase again, then a distinct phrase, then the first phrase again.

Pass criteria:

- [ ] Every audible phrase matches the request order.
- [ ] Exactly the existing two service-owned dynamic TTS identities remain in use.
- [ ] No stale or cross-request audio is heard.
- [ ] Existing resident-content/boot-continuity safety remains intact.

## Gate 3 — accepted non-MP3 media normalization

Use one short Home Assistant media-source clip in an accepted non-MP3 format, preferably WAV or FLAC.

Pass criteria:

- [ ] HA resolves and forwards bounded bytes.
- [ ] Backend normalization succeeds.
- [ ] Intended Smart Chime plays the correct audio.
- [ ] No additional Protect ringtone identity is allocated per media item.

Record input MIME type and approximate clip duration without embedding the media itself.

## Gate 4 — native `tts.speak` to physically validated G3 Instant

Target only the established physically validated UVC G3 Instant.

Pass criteria:

- [ ] `/targets` reports the established validated exact profile before playback.
- [ ] The media request reaches the same hardened camera talkback path as text announcements.
- [ ] The expected phrase is audibly heard once and only once.
- [ ] No Smart Chime slot write occurs for a camera-only request.
- [ ] No automatic retry occurs after any uncertain post-send condition.

## Gate 5 — mixed Smart Chime + validated camera group

Use one short, unique native `tts.speak` phrase against an explicitly configured mixed group.

Pass criteria:

- [ ] Both intended physical targets receive the same requested content.
- [ ] Camera capability restrictions remain enforced.
- [ ] Chime fixed-slot ownership remains enforced.
- [ ] No unrelated device plays audio.
- [ ] Any partial failure is represented as `partial`/failure rather than falsely flattened to success.

## Gate 6 — rejection before physical playback

Test each case separately against an otherwise valid target:

- [ ] body larger than configured `MEDIA_MAX_INPUT_BYTES` → rejected before dispatch/playback;
- [ ] duration over `MEDIA_MAX_DURATION_SECONDS` → rejected before device preparation/playback;
- [ ] unsupported declared MIME type → rejected before decode/dispatch;
- [ ] invalid bytes under a supported MIME type → rejected before device preparation/playback;
- [ ] compressed request body → rejected;
- [ ] missing/bad application API key → rejected;
- [ ] arbitrary direct URL supplied to the HA media player → rejected rather than fetched.

Pass criteria: no physical device emits audio for any rejection case.

## Gate 7 — text/media concurrency isolation

Exercise one normal Announcer-side text request and one media-source request close together. If practical, repeat with two media requests to different targets.

Pass criteria:

- [ ] Normal text still invokes the configured backend TTS engine.
- [ ] Media playback uses its own uploaded normalized payload.
- [ ] No request receives another task's audio bytes.
- [ ] Queue ordering remains deterministic for the same physical target.
- [ ] Separate physical target queues remain independent.

## Gate 8 — recovery and regression smoke
