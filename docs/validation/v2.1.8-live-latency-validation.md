# UniFi Announcer v2.1.8 Candidate — Live Latency Validation

## Final gate

```text
RESULT: FAIL — do not merge
```

PR #32 meets the resident-latency goal and correctly avoids redundant writes during normal operation and an Announcer-only restart. It fails the required physical Smart Chime reboot safety gate: after the Chime rebooted, the candidate reported a trusted content hit, skipped the upload, and the device played a single electrical tone instead of the requested phrase.

## Smart Chime reboot behavior — blocking failure

Immediately before reboot, A was a trusted resident content hit. The supported, confirmation-guarded Chime reboot endpoint was invoked once. No reset, re-adoption, credential change, or reprovisioning occurred.

The Chime returned connected and healthy. A post-reboot request then reported:

```text
content_hit: true
selection_content_match: true
overwrites: 0
overwrite_skips: 1
slot_direct_upload_ms: 0
slot_sync_ms: 0
slot_settle_ms: 0
slot_prepare_ms: approximately 50 ms
uploadRingtone calls: 0
```

The first post-reboot sound was not conclusively heard. A second resident replay was therefore requested. It completed in 643 ms and again skipped upload. The user physically heard **a single electrical tone**, not `Unifi chime test`.

This demonstrates that the physical Chime's playable slot content cannot be assumed to survive reboot merely because:

- the device MAC/serial/static identity is unchanged;
- the logical-to-physical slot mapping and filename remain unchanged;
- the Announcer registry and content-state records agree;
- Protect still reports the same slot identity.

The candidate retained stale application-authoritative content proof across the hardware reboot and played incorrect audio. This is an immediate release blocker.

## Root cause in the candidate

`app/playback/production_slots.py` builds `_device_identity()` from static fields such as MAC, serial/device ID, and firmware (approximately lines 148–174). Those values do not change when the same physical Chime reboots.

At startup, persisted content is trusted when that static identity and registry/content records match (approximately lines 236–275). During `prepare()`, the trusted application record is sufficient to skip the physical overwrite after slot preflight (approximately lines 369–385).

The preflight proves the owned slot mapping/filename, but it does not prove that the physical slot still contains the expected audio bytes after a Chime reboot. Because Protect's content metadata is stale in this environment, the candidate has no reliable evidence that the audio survived. The application record remains trusted and the upload is incorrectly skipped.

## Required engineering action

1. **Invalidate all resident content proof before Announcer's supported `/reboot` action sends the Chime reboot request.** Persist the invalidation before issuing the reboot so a process crash cannot resurrect it.
2. **Invalidate content proof on any observed Chime offline → online/reconnect epoch**, covering external power loss or reboot paths not initiated through Announcer.
3. If the direct device API exposes a reliable boot identifier or monotonic uptime, tie trusted content to that boot epoch. Static MAC/serial/firmware identity is insufficient.
4. If boot continuity cannot be proven, fail safe: preserve the two owned slot identities but force one rewrite per resident phrase after a Chime reconnect/reboot.
5. Add a regression test where:
   - device identity remains unchanged;
   - logical/physical slot and filename remain unchanged;
   - reboot clears or replaces physical playable content;
   - the next prepare must be a content miss and perform an overwrite;
   - wrong/stale playback is impossible.
6. Preserve the successful Announcer-only restart optimization when boot continuity is provably unchanged.
7. Do not weaken preflight/ownership checks or lower timing guards further to compensate.
8. Before a release, align the backend semantic version with `2.1.8`; this candidate currently reports `2.1.7` despite carrying the v2.1.8 performance work.

## Final recommendation

Keep PR #32 draft. Fix reboot/reconnect invalidation, rerun automated tests, then repeat the physical Smart Chime reboot gate. Normal resident reuse and latency are excellent, but correct audio after hardware lifecycle events is a higher-priority requirement.
