# REA Chime reliability audit — 2026-10-24

This audit found additional non-security reliability issues after the October 10 single-Chime listening checks. The most consequential discovery is that **Protect can restore its canonical ringtone bytes into an Announcer-owned slot without a Chime reboot**. Announcer currently treats some such slots as still containing cached speech. A second controller behavior matters: **a missing requested ringtone can fall back to built-in track 1 and still return HTTP 200**.

This report records findings against the October 24 commits below. The subsequent [October 25 offline repairs](offline-repairs-2026-10-25.md) implement most repairs and describe remaining limits; the original reproduction descriptions remain historical evidence. No playback, upload, reboot, adoption, device configuration, deployment, or service restart was performed during the audit. Live activity was limited to read-only status requests and copying the shipped controller JavaScript/package metadata. All failure scenarios ran locally with synthetic state and fake device operations. No new acoustic validation is claimed.

## Findings, in recommended repair order

Priorities describe practical reliability impact: P1 should be resolved before relying on the affected guarantee; P2 is an important correctness defect or bounded contract correction. “Reproduced” below means isolated software execution unless explicitly stated otherwise.

### 1. Protect resynchronization can replace cached speech — P1 / STATE-5

The shipped controller subscribes to ringtone creation and deletion, then synchronizes all adopted, connected Chimes. Its synchronizer compares each canonical ringtone's MD5 and track number with the device inventory. A mismatch causes the canonical file to be uploaded. Connection initialization also performs this synchronization.

Current module chain: `825771` registers listeners → `221142` / `67165` handle ringtone creation/deletion → `946642` chooses mismatches → `486268` reads canonical bytes and uploads them. Module `713414` handles reconnect initialization. Corresponding 7.2.105 modules exhibit the same behavior.

An offline execution of the exact current creation/synchronization factories requested a canonical upload to an existing speech slot whose filename and slot number had not changed. A separate probe of the real Announcer slot manager simulated that replacement, including fresh inventory MD5 matching the replaced bytes. Announcer reported `content_hit=true`, performed no second write, and retained its obsolete speech fingerprint. Ringtone-add and connected-to-connected inventory events triggered no invalidation.

The underlying code checks slot ownership separately from content, but same-filename preflight can disregard changed inventory fingerprints (`app/playback/dynamic_slots.py:416`), and cached content can then skip the write (`production_slots.py:523`). The event stream omits ringtone events and only reacts to a known disconnected-to-connected Chime transition (`app/main.py:1275`, `1404`). Announcer's canonical slot content is silent bootstrap audio (`app/server.py:127`), making silence a plausible symptom after restoration. That audible outcome was **not** tested here.

**Repair direction:** Treat Protect as another writer. Coordinate ringtone mutations, account for missed/reconnection events, and define when resident-content evidence is fresh enough to reuse. Merely invalidating once after preset creation is insufficient: Protect synchronization can complete asynchronously afterward. Do not weaken ownership checks or treat every conflicting MD5 as stale inventory.

**October 25 repair boundary:** Resident reuse now requires a matching inventory fingerprint, and controller events revoke active proof. The existing post-write fallback for delayed Protect inventory remains: an acknowledged direct write to an exactly owned slot can proceed after the bounded synchronization wait. If a controller restoration occurs with the same filename and its event is missed, that fallback cannot distinguish the replacement from delayed metadata. This is a remaining device/content-certainty gap, separate from the ordinary-preset filename-mapping gap below.

### 2. Missing ringtone can return success with a different tone — P1 / CTRL-1

Current module `304020` starts with built-in track 1. If file lookup succeeds but the named track is absent from `speakerTrackList`, it logs the fallback and still sends track 1. If file lookup fails and no record supplies a track number, it also retains track 1. The REST route in `530307` returns success when this handler resolves; it does not verify that the requested ringtone was selected.

An isolated execution of the exact route handler and playback factory returned **HTTP 200 / track 1** for both missing-ID and missing-device-track fixtures, using otherwise valid audio payloads. This is not a live request.

Announcer raises `StaleRingtoneError` only for selected explicit 400/404 responses (`app/main.py:354`), and the dispatcher refreshes identity only on that exception (`app/dispatcher.py:309`). A successful controller fallback bypasses that recovery.

**Repair direction:** Validate requested identity and device availability before playback, including refresh/recovery when evidence is missing. Preserve the distinction between request acceptance and actual audio. Preflight alone cannot eliminate a subsequent controller/device race; document the residual limit rather than promising acoustic certainty.

**October 25 offline contract follow-up:** Protect `7.3.70` module `875359` confirms that `GET /api/ringtones/:id` returns the canonical MP3 bytes, and returns HTTP 400 when the record is missing. Module `505937` retains the uploaded MP3 bytes while generating a separate OGG representation, so hashing the canonical MP3 is a valid content comparison. However, an inventory row with that hash does **not** prove the requested record resolves to that row's filename or physical slot. Identical audio can have multiple identities; `filename`, `trackNo`, and `md5` are private on the public ringtone model (`811338`). File-storage IDs and legacy ringtone IDs are separate identities (`212364`, `749134`). Ordinary-preset hash preflight therefore reduces known missing-content failures but cannot establish exact routing or exclude all successful wrong-tone outcomes. Do not invent a filename from the ringtone ID. The owned dynamic-slot path has separately journaled filename/physical-slot evidence and requires an active prepared lease; even there, controller changes after the last observation remain a race requiring physical validation.

### 3. Interrupted first provisioning can remain unrecoverable — P1 / STATE-1

If staging succeeds but the first following inventory response is lost, the persisted slot has no completed binding. A retry snapshots the already-staged state, stages identical bytes, and finds no new delta to prove. The probe injected one lost response, then allowed two healthy retries: **one upload, three staging calls, zero bindings**, readiness false throughout (`app/playback/fixed_slots.py:223–291`). This assumes idempotent physical restaging; hardware behavior still needs a later check.

**Repair direction:** Persist enough operation evidence to resume safely after an ambiguous completion, or provide an explicit proven repair transaction. Keep the refusal to guess ownership.

### 4. Restart loses active playback reservations — P1 / STATE-2

Target timers and busy-slot leases are process-local. Shutdown cancels them, and startup restores content identity without restoring playback deadlines (`app/playback/admission.py:142`, `dynamic_slots.py:252`, `app/server.py:392`). A synthetic 10-second announcement admitted the same target and re-leased its slot about **0.132 seconds** after a simulated restart, with about 9.868 seconds remaining on its original estimate.

This proves loss of the software guard, not actual audible overlap. The October 10 restart check occurred after completed playback and does not cover this case.

**Repair direction:** Durable conservative playback deadlines or an equivalent startup quarantine, covering crashes as well as graceful restarts.

### 5. Preset replacement can destroy the previous recording before failure — P2 / C1

`create_or_update_preset()` deletes the existing ringtone before the new upload succeeds, and ignores a rejected deletion (`app/main.py:1212–1243`). An upload-failure probe left no recording while the registry still pointed to the deleted ID. A rejected-delete probe still attempted upload; when the fake controller allowed duplicate names, both recordings remained.

**Repair direction:** A recoverable replacement transaction with explicit full-capacity behavior, confirmed deletion semantics, and registry commit only after identity is established. The ignored-deletion problem is independent of whether a real controller accepts duplicate names.

### 6. Duration metadata can describe the wrong preset identity — P2 / C2

The dispatcher trusts a preset duration by name without checking its recorded ringtone ID against the selected ID (`app/dispatcher.py:341`). A probe played `new-long-id` while using a 1-second duration belonging to `old-short-id`, producing a **2.25-second** hold instead of the configured 30-second unknown-duration fallback. Stale-ID retry can also change identity after the guard is computed.

**Repair direction:** Bind duration evidence to recording identity/content; invalidate it when identity changes and extend existing holds conservatively when necessary.

### 7. Malformed optional content cache prevents preparation — P2 / STATE-3

The loader accepts invalid nested binding values. Later updates fail after a physical write has already been attempted (`app/playback/production_slots.py:88`, `539`, `589`). A valid-JSON fixture containing string rows reported ready, then two requests both failed with `TypeError` after two fake writes.

**Repair direction:** Fully validate optional cache structure and discard malformed optimization records while retaining the separate ownership registry.

### 8. Recovery exposes readiness before restoration completes — P2 / STATE-4

The superclass sets `ready=true` before an awaited migration; the production subclass restores content state only after the superclass returns (`fixed_slots.py:67`, `production_slots.py:358`). Background recovery serves requests concurrently. A paused-migration probe accepted preparation while startup was incomplete and device identity restoration had not run.

**Repair direction:** Publish readiness once at the end of the complete production startup/recovery transaction.

### 9. Saving a legacy dynamic key as a preset retains eviction eligibility — P2 / C3

Reusing an existing record changes its ID/duration but not `kind` (`app/main.py:1239`). A legacy `dynamic_tts` record saved through the preset operation remained eligible for later capacity eviction, which the probe demonstrated. This requires a legacy logical-key collision; none is asserted in current user data.

**Repair direction:** Make conversion to a persistent preset an explicit classification transition.

### 10. Multiple HA instances share a service with singleton behavior — P2 / C4

Different backend URLs are permitted, but the global service routes through `entries[0]`; unloading either instance removes the shared service (`custom_components/unifi_announcer/__init__.py:81`, `106`). A two-entry probe sent a second-instance target to the first client, then removed the service while the first remained configured.

**Repair direction:** Explicit instance routing and lifetime management, or a clearly enforced single-instance contract. This does not claim the current installation has multiple instances.

## Additional controller contract corrections

- **“Assigned default” means built-in track 1 on this manual playback route.** Omitting `ringtoneId` does not consult per-camera `ringSettings` in either inspected version. The current exact-handler fixture included a custom camera assignment and still selected track 1. Documentation should distinguish manual default-tone playback from a doorbell camera's assigned ringtone. Existing UI labels are not renamed by this audit.
- **An omitted repeat count is not bounded by Announcer's explicit 1..6 policy.** The controller's audio validator accepts 1..10, and playback inherits `chime.repeatTimes` when omitted. Announcer's comment/guard assumes at most six. The offline fixture forwarded 10; the actual configured device snapshot was 1. The default 30-second duration estimate may compensate for short tones, so no physical overlap is inferred solely from the repeat mismatch. Resolve the setting or use a defensible bound.
- **Catalog capacity and physical slots are different.** Current module `811338` defines built-in slots 1..4, custom slots 5..10, and a separate maximum of 12 custom catalog records. A successful catalog upload does not prove a distinct resident slot exists. These controller constants do not invalidate a lower practical capacity limit observed elsewhere.
- **Firmware family mapping is now supported by controller code.** Module `915458` explicitly maps `UP Chime` to `esp32` / Smart WiFi Chime and `UP Chime PoE` to `esp32-d0wd` / Smart PoE Chime. This resolves the old “PoE-ish” label at the controller-model level; it does not prove interchangeable firmware or shared hardware behavior.
- **Native Protect text-to-speech is still not a proven Smart Chime path.** Current module `104293` uses speaker/integration models, not a Chime text endpoint. No automation “dry run” was invoked; that label does not guarantee silence.
- **Direct-upload completion remains an open question.** Protect's upload client sends raw bytes and allows 120 seconds; Announcer uses its shorter direct timeout. This is a contract difference, not proof that any particular upload fails. Native completion semantics, accepted writes after client cancellation, and exact byte limits need separate validation.

## CI implications and media branch

The relevant existing state regression subset still passed: **45 tests in 4.27 seconds**. The new failure probes explain coverage gaps despite green tests; they do not justify restoring obsolete prose snapshots or import/mock benchmark tests.

Add focused regressions alongside each repair: controller restoration after a successful direct write; successful wrong-tone fallback; lost response after staging; restart during active playback; failed preset replacement; mismatched duration identity; malformed nested cache state; readiness interleaving; legacy preset conversion; and two-instance HA lifecycle. Use deterministic fakes/barriers, not long sleeps or live hardware in routine CI.

On the separate media branch, normalization launches ffprobe/ffmpeg **before dispatcher admission** (`app/routes/media.py:70–74`). Integrating bounded admission must also bound this earlier work; otherwise suppressed/deduplicated/dropped requests can still consume decoder resources. This is a confirmed call-order gap, not a reproduced exhaustion incident. A short synthetic WAV-to-MP3 check in the built image adds coverage that mocked normalization tests and a Docker build alone do not provide. Keep minimum/current HA compatibility jobs; this audit offers no evidence that either is redundant.
