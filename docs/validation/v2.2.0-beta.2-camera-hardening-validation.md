## Physical playback gates

### 1. Normal speech

- [ ] Send one short unique text announcement through Home Assistant.
- [ ] Confirm clear, intelligible speech from the intended G3 Instant.
- [ ] Confirm HA Last playback result is success.
- [ ] Confirm camera queue returns to zero.

### 2. Repeat behavior

- [ ] Send one request with `repeat_times=2`.
- [ ] Confirm exactly two repetitions.
- [ ] Confirm repetitions are sequential and non-overlapping.
- [ ] Confirm no unexpected third replay/retry.

### 3. Same-camera concurrency/session serialization

Send two distinct requests to the same camera close enough together that the second arrives while the first request is still preparing/playing.

- [ ] Both requests ultimately speak the correct respective text.
- [ ] No overlapping audio is heard.
- [ ] No wrong/stale phrase is heard.
- [ ] No duplicate/retry is heard.
- [ ] Logs/metrics show only one prepared physical talkback session at a time for that camera.
- [ ] The second request waits rather than opening a competing talkback session.

Repeat once with different priorities if practical; priority must not create overlapping physical sessions.

### 4. Dynamic offline → online recovery

- [ ] Make the configured camera unavailable using a reversible, non-destructive method.
- [ ] Without restarting Announcer, poll authenticated `/targets` and confirm `status=unavailable` / `announce=false`.
- [ ] Confirm existing HA camera announcement entities become unavailable; do not reload the integration.
- [ ] Restore the camera.
- [ ] Without restarting Announcer or reloading HA, wait for normal polling and confirm `/targets` returns `status=available` / `announce=true`.
- [ ] Confirm the same existing HA entities become available again.
- [ ] Send an announcement and confirm clear/correct speech.

### 5. Valid mixed Smart Chime + camera group

- [ ] Use a valid group containing the existing Smart Chime and G3 Instant.
- [ ] Send one short unique announcement.
- [ ] Confirm correct speech from both devices.
- [ ] Confirm group result is successful rather than partial/failed.

### 6. Unavailable mixed-group fail-closed behavior

Use a reversible unavailable-camera condition; do not introduce an unknown group member because beta.2 now rejects that configuration at startup.

- [ ] Record Smart Chime slot-status fingerprint/overwrite counters before the request.
- [ ] Make the camera unavailable and confirm `/targets` reflects unavailable.
- [ ] Send the mixed-group announcement.
- [ ] Confirm the request fails before Smart Chime playback.
- [ ] Confirm no Smart Chime slot overwrite/preparation occurred.
- [ ] Confirm no speech was emitted from the Smart Chime.
- [ ] Restore the camera and confirm the valid group works again.

### 7. Camera-only Smart Chime isolation

- [ ] Capture `/tts/slots/status` before camera-only playback.
- [ ] Play one camera-only announcement.
- [ ] Confirm correct camera speech.
- [ ] Capture `/tts/slots/status` afterward.
- [ ] Confirm no Smart Chime content/slot mutation attributable to the camera request.

### 8. Announcer restart

- [ ] Restart/recreate only the Announcer service using the same exact candidate image.
- [ ] Confirm `/version` and OCI revision still match the candidate.
- [ ] Confirm camera capability is revalidated as available.
- [ ] Send a new camera announcement and confirm clear/correct speech.
